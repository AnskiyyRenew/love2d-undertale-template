    🔧 STI and Tilesets

    Map files are read by the engine's built-in STI (Scripts/Libraries/STI/). It is a general-purpose library, not written for this engine, so there are two hard constraints that must be obeyed — violating them doesn't mean "drawing a bit less", but that the entire Overworld fails to load.

    Hard Constraint 1: Tilesets must be embedded in the map¶

    When STI loads tilesets, it has this line:

    assert(not tileset.filename, "STI does not support external Tilesets.\nYou need to embed all Tilesets.")

    In other words: tilesets cannot exist as external .tsx files, they must be embedded in the map.

    How to choose in Tiled Exported .lua
    ✅ Embedded in map Keep the default Embed in map when creating a tileset; for an already-external one, right-click in the tileset panel → Embed Tileset tilesets has no filename
    ❌ External tileset Checked "Save as external tileset file (.tsx)" when creating One extra line filename = "xxx.tsx"

    Hitting this triggers an assert crash

    Using an external tileset, the sti(map.current, {"box2d"}) inside Map.Init will directly throw the English error above, interrupting scene loading.
    It happens the instant you enter the scene, and is easily misdiagnosed as "the map file is broken".
    How to check: open the exported .lua and search for filename — as long as there is this line in tilesets, it wasn't embedded.

    Each map stores its own copy

    Embedding applies to a single map, so each .lua repeats a section of tilesets definition.
    This is a hard requirement of STI that cannot be bypassed; the only cost is a slightly larger export file, and the tile images themselves are not duplicated.

    Hard Constraint 2: Tiles are 20 × 20¶

    The standard tile size in UNDERTALE is 20 × 20 pixels — copy this when creating a new map:

    Item Value
    Map Tile Size 20 x 20
    Tileset Tile Size 20 x 20
    Margin / Spacing 0 / 0

    The engine draws the map at 2× scale, so:

    • One tile occupies 40 × 40 pixels on a 640 x 480 canvas;
    • One screen shows 16 × 12 cells;
    • The default 30 x 20 cell map = world coordinates 1200 x 800.

    Filling it wrong won't error

    The engine does not validate this number. Setting tiles to 16 or 32, the game still runs, but the terrain won't align to the grid, and seams or misalignment appear between sprites — very tedious to troubleshoot.

    Large decorations can be exceptions

    Not every tile needs to be 20 × 20. Whole pieces of furniture like beds and pianos can use a separately-sized tileset (the engine's own Maps/main_scene/main_0.lua has a 50 x 68 bed).
    But all tiles within the same tileset must be the same size — don't stuff furniture into the terrain tileset.

    Tile Image Paths¶

    This is how STI assembles the image path:

    utils.format_path(path .. tileset.image)   -- path = the directory of the map .lua
    • The path is relative to the map's .lua file, not to the project root.
    • The image is read directly from disk by love.image.newImageData(), not through Sprites' resource resolution.

    From this, three rules follow:

    Don't export the .lua to another directory

    The .tmx and the exported .lua must be placed in the same directory (or at the same relative depth).
    Exporting to a different directory makes the relative path written by Tiled invalid, manifesting as an entirely empty map with no error at all.

    When overriding a map in the Game area, the tile images aren't overridden too

    Game/Maps/xxx.lua can override Maps/xxx.lua, but its image is still looked up on the Game/Maps/ side.
    So when you put a map in the Game area, you must also copy its tile images there at the same relative path.

    File names are case-sensitive

    Tile image paths are case-sensitive — it runs on Windows, but when packaged to Android / Linux the whole map turns white.
    Also use only ASCII in paths; avoid Chinese directory names.

    Animated Tiles¶

    UNDERTALE's water, torches, and waterfalls are all animated tiles. To make an animated tile in Tiled:

    1. Double-click the tileset in the Tilesets panel to open the tileset editor (just selecting it in the map is not enough).
    2. Select the cell to be the animation "host" — this is the cell you paint on the map.
    3. Open the animation editor: menu Tile → Animation (in some versions it's under the Tileset menu; in the Chinese UI it's "Tile → Animation"), or click the film-strip icon on the tileset editor toolbar; a timeline expands below the tileset view.
    4. Drag each frame from the tileset into the timeline; drag to reorder.
    5. Below each frame on the timeline is that frame's duration (milliseconds), which you can click to edit. Tiled previews it looping.
    6. Export the .lua.

    After export, that cell gets an extra section in tiles:

    tiles = {
  {
    id = 12,
    animation = {
      { duration = 150, tileid = 12 },
      { duration = 150, tileid = 13 },
      { duration = 150, tileid = 14 },
    }
  }
}

    No work is needed on the engine side — map.lua's Map.Update already calls map._map:update(dt), and STI will accumulate the time, advance the frame, and push the new frame's quad back into the sprite batch on its own.

    STI's advancement logic (STI/init.lua's Map:update) 
    tile.time = tile.time + dt * 1000          -- dt is seconds, multiply by 1000 to get milliseconds
while tile.time > tonumber(tile.animation[tile.frame].duration) do
    tile.time  = tile.time - duration
    tile.frame = tile.frame + 1
    if tile.frame > #tile.animation then tile.frame = 1 end
end
-- after advancing the frame: write the new frame's quad back into the sprite batch of all instances
local t = self.tiles[tile.animation[tile.frame].tileid + self.tilesets[tile.tileset].firstgid]
j.batch:set(j.id, t.quad, j.x, j.y, j.r, tile.sx, tile.sy, 0, j.oy)

    Four pitfalls of animated tiles¶

    Duration unit is milliseconds

    The 150 filled in the timeline is 150 milliseconds, not 0.15 nor 150 frames. To make a cell stay for 0.5 seconds, fill in 500.

    Animation frames must come from the same tileset

    STI computes the frame's gid via tileid + firstgid, and this firstgid comes from the host cell's tileset.
    Cross-tileset references fetch completely unrelated cells — no error, just weird patterns drawn.

    All instances are always in phase

    STI advances the animation by tile (gid), not by "each instance placed on the map".
    So all the same animated tile in one map will play together in sync — you can't get the effect of water flow or flames with staggered phases.
    To stagger them, copy the frames to make a second animated tile and place them manually offset.

    Unused animations cost no performance

    Map:update only refreshes the batch when self.tileInstances[tile.gid] exists — i.e. only tiles actually painted on the map go through this.
    Animations that are defined but never placed won't slow down the frame rate.

    Animation is visual only

    Animated tiles don't participate in collision and produce no runtime objects — collision is entirely determined by object layers. See Maps and Object Layers.

    A pit that can ruin the entire map: a leaked setColor¶

    STI draws tiles using lg.setColor(r, g, b, a * layer.opacity) inside Map.drawLayer — in other words, it uses whatever color is currently in the environment.

    And LÖVE's default love.run does not reset the drawing state between frames (it only calls origin() and clear()). So:

    As long as you setColor in some frame and forget to restore it, that color will leak across frames, becoming the "ambient color" of the next frame, tinting the entire map with color / transparency.

    The engine has already handled one real accident, in the virtual keyboard:

    -- Scripts/Libraries/Controller/VirtualKeyboard.lua  Draw()  at the end
-- The default love.run does NOT reset the graphics state between frames (it only
-- calls origin() + clear()). The colour left behind here therefore became the
-- ambient colour of the NEXT frame -- and STI paints the tilemap with that
-- ambient colour ... so a leaked tint made every map tile render translucent
-- (once into STI's own map canvas, once again when that canvas is blitted back).
SE.graphics.setColor(1, 1, 1, 1)

    Do the same when drawing your own HUD / dialog boxes

    The rule is simple: wherever you setColor, restore the color to (1, 1, 1, 1) after drawing.
    The symptom is "the map suddenly became semi-transparent / turned red", a problem that looks completely unrelated to your code, and is very hard to trace. Same for fonts — restore setFont at frame end too.
